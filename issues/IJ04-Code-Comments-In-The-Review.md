# IJ04 — Code comments in the review

**Status:** Implementing.
**Size:** L - SARIF 2.1.0 through Porelo's hardened profile reader, the comment calls and the push's level, class and review summary in `Gate`, inline diff threads through [IJ12](README.md#ij12)'s adapter, a discussion panel in `ReviewEditor` for file, general and outdated threads, read-only fix previews, and source-level, risk-class and completeness badges; the `collaborationTools` adapter ([IJ12](README.md#ij12)) and held or outgoing forge comments, `toForge` included ([IJ13](README.md#ij13)), are split out.

**What must be true.** A developer who reviews waiting work in IntelliJ comments and proposes line replacements on its diff, files, or review using IntelliJ's code-review gutter and inlays, and reads in the same place what checking and building agents, linters, and people on a forge said, all carried as SARIF 2.1.0 and marked with their authenticated source level, origin, and the push's risk class. The interface shows only the counts of open findings and threads per push and writes no comment, so the review tab is the one place where a comment is written, answered, resolved and read at its line, file or review.

## The shape

### 1. The daemon's calls on `org.fuin.porelo.Tasks1`

Every call takes `project`, `repository` and the push's `name`, as the gate calls do today. A field marked `?` is absent, never empty; a field the plugin does not know is ignored, and an enumeration value it does not know is shown as the daemon's word, never fatal. SARIF travels as one UTF-8 JSON string field `sarif`, one document of Porelo's review profile: one run, at most 100 results, 1 MiB.

- **`Pending`** gains on each push `sourceLevel: ?string` (`E0`, `E1`, `I1`, `A` or `unknown`; `unknown` and absent are shown and treated at least as `E0`), `sourceWords: ?string`, `riskClass: ?string` (`C0` to `C3`, the highest class among the changed files), `approvalsNeeded: ?int` (1, or 2 for `E0`, `unknown` or `C3`), `task: ?string`, and `review: ?ReviewSummary`:
  - `ReviewSummary(round: int, openFindings: int, openThreads: int, heldInbound: int, waitingOutbound: int, runs: []ReviewRun)`;
  - `ReviewRun(run: string, name: string, kind: string, state: string, findings: int, openFindings: int)`, `kind` in `person`, `task`, `forge`, `scanner`, `state` in `complete`, `partial`, `failed`, `unknown`, `running` or `not-run`.
- **`Review`** gains `base: ?string`, the full commit it diffed against, and each file `riskClass: ?string`; an absent class is shown as `-`, never as `C0`.
- **`Comment(project, repository, name, sarif, replyTo: ?string, toForge: ?bool, id: ?string) -> (guid, thread, sarif, forgeComment: ?ForgeComment)`** stores one result. `replyTo` is the `guid` of the result a reply answers, in any run of the push; `id` (`[A-Za-z0-9._-]{1,64}`) makes a retry with the same document answer the same comment, never a second one. `toForge` and `forgeComment` are [IJ13](README.md#ij13)'s; this issue never sets `toForge`.
- **`Comments(project, repository, name, run, round: ?int, cursor: ?string) -> (sarif, cursor: ?string)`** pages one run: one document of at most 100 results each page, the cursor absent on the last. Only the last page's `porelo/completeness` speaks for the run. An earlier `round` answers that round's runs as they were, outdated results marked.
- **`ResolveThread(project, repository, name, thread, reopen: ?bool) -> (thread, state)`** sets a thread `open` or `resolved`. It only shows the thread resolved: it clears no finding, changes no approval and approves nothing.
- **Refusals**, each a named error the plugin says in words: `NoSuchPush(name)`, `MovedSinceReview(name, reviewed, now)` (as today, also when the run's base is not the base `Review` answered), `ProfileViolation(detail, rule, path)`, `ForbiddenField(detail, path)`, `TooLarge(detail, limit, path)`, `UnsafeText(detail, path)`, `AnchorOutsideBlob(path, startLine, endLine)`, `FixOutsideAnchor(detail, path)`, `OldSideFix(detail, path)`, `NoSuchResult(guid)`, `NoSuchThread(thread)`, `CursorRefused(cursor)`, `IdReused(id)`. Anything else is the daemon's own words, as today.

### 2. What the plugin sends and what it reads

- **What a person's comment carries** (the profile's column for a person's client), and nothing else: root `version: "2.1.0"` and `properties["porelo/profileVersion"]: "1"`; one run with `tool.driver.name` (the plugin; it claims nothing), `versionControlProvenance[0].revisionId` (the push's commit), `columnKind: "unicodeCodePoints"` and `run.properties["porelo/baseRevisionId"]` (the base `Review` answered); one result with `kind: "review"`, `level: "none"`, `message.text`, optional `message.markdown`, `locations` (`artifactLocation.uri`, `region` with `startLine`, `endLine`), `properties["porelo/anchorKind"]` (`line`, `file` or `general`), `properties["porelo/diffSide"]` (`old` or `new`; required on `line`, absent on `general`), and an optional fix. A literal `{` or `}` in a message is written doubled.
- **What the daemon stamps, which the plugin never sends:** `repositoryUri`, `guid`, `porelo/threadId`, `porelo/replyTo`, `porelo/threadState`, `porelo/sourceKind`, `porelo/sourceLevel` (`I1` for a comment written here), `porelo/authorId`, `porelo/authorDisplayName`, `porelo/taskId`, `porelo/taskRole`, `porelo/completeness`, `porelo/projectId`, `porelo/repositoryId` and `porelo/reviewRound`. Sending one is refused `ForbiddenField`, so the writer builds the document from the allowed fields only.
- **What the plugin reads** from each result: `guid`, `kind`, `level`, `ruleId`, `message.text`, `message.markdown`, the anchor, `fixes`, `porelo/threadId`, `porelo/replyTo`, `porelo/threadState`, the author keys (`porelo/sourceKind`, `porelo/sourceLevel`, `porelo/authorDisplayName`, `porelo/taskId`, `porelo/taskRole`, `porelo/forgeInstanceId`), `porelo/outdated`, `porelo/outdatedReason` and the original-anchor fields (`porelo/originalRevisionId`, `porelo/originalPath`, `porelo/originalStartLine`, `porelo/originalEndLine`, `porelo/originalDiffSide`), and `porelo/draft`; from the run `porelo/completeness`, `porelo/reviewRound` and `porelo/reviewVerdict` (evidence only).
- **A line-replacement suggestion** is `result.fixes[0].artifactChanges[0].replacements[0]` (`deletedRegion`, `insertedContent.text`): one replacement on the `new` side of a regular blob, whose region equals the anchor, `insertedContent.text` at most the anchor's lines plus 10, 400 characters a line and 8 KiB.

### 3. Diff threads, discussion panel and read-only fix previews

- In `ReviewEditor`, a line or a range of up to 100 inclusive lines on the `old` or `new` side of the diff takes a comment and an optional replacement suggestion, and existing `line` threads of the current round are rendered beside their lines through [IJ12](README.md#ij12)'s `Threads` adapter.
- File comments (`file`, without a `region`), general review comments (`general`, without `locations`), and outdated threads (`porelo/outdated: true`, or a `line` result without a current place) are shown in a discussion panel in `ReviewEditor`.
- A suggestion is shown inside its comment as a read-only `SimpleDiffRequest` preview computed in memory over the cached blob. The plugin never applies a suggestion to a document or working tree: the agent applies it in its task, and the result returns through the gate as a new push.
- `Decisions.reject` drops the push with the person's reason, and the daemon delivers the open threads to the task as structured review data.

### 4. Security requirements

- **Hardened SARIF reading and writing:** Read every `sarif` field with Porelo's hardened profile reader before anything binds it, with the profile's limits taken from there and never copied: a document of 1 MiB, one run, 100 results, depth 24 and 100,000 tokens; 32 KiB a result, 8 KiB a body, 16,384 characters a string; duplicate keys, trailing tokens, unknown or forbidden fields, coercions, numeric enums, unknown enum fallbacks and class-name polymorphism refused. Drop nothing silently and round-trip no untrusted object graph: a comment is written from fresh model objects and the written document is read again by the same reader before it is sent.
- **Characters:** refuse Unicode format characters (bidi controls, zero-width characters, tag characters, soft hyphen), variation selectors, unpaired surrogates, noncharacters and control characters other than line feed and tab in every string of a document read or written.
- **Git-tree anchor resolution in the bare cache:** Validate `artifactLocation.uri` as a canonical repository-relative path (decode once, re-encode and compare, at most 1,024 decoded bytes; schemes, authority, absolute paths, backslashes, drive prefixes, queries, fragments, empty or dot components, encoded separators, decoded percent signs, and control or format characters refused) and resolve it only against pinned regular blobs in `ReviewCache`: `changes.commit()` matching `revisionId` for `new`, `changes.base()` matching `porelo/baseRevisionId` for `old`. Never fetch `$schema`, `hostedViewerUri` or a remote avatar, and never resolve a path against the host file system or an open IDE project.
- **Safe comment rendering:** Render only the profile's Markdown subset (paragraphs, simple lists, emphasis, code) with all network access disabled (no image loading, no raw HTML, no links, no `jetbrains://` links), or the plain `message.text` where the subset cannot be rendered safely. Render the daemon-stamped origin (`porelo/sourceKind`, `porelo/authorDisplayName`, `porelo/taskId`, `porelo/taskRole`) and the source-level badge (`E0`, `E1`, `I1`, `A`) in header components outside the untrusted body.
- **Suggestion confinement:** Admit at most one fix, one change and one replacement on the `new` side of a regular blob, whose `deletedRegion` equals the anchor. Outdated, `old`-side or `E0` suggestions have no actionable control, and every fix preview is read-only with no apply action.
- **State and authority separation:** Resolving a thread here changes only what is shown; a gate finding is cleared only by the person's confirmation in the daemon, or, as [IJ13](README.md#ij13) shows, by a forge thread resolved by an `I1` account. Keep `porelo/threadState` apart from `suppressions`, `porelo/reviewVerdict`, `baselineState`, the counts, and `Gate.approve`, which binds to the push's commit. Show each run's `state` in the daemon's word, and a clean review only for `complete` with no findings, so a partial, failed, running or missing run never looks clean. Show the push's source level, risk class and `approvalsNeeded` in `WaitingTree` and `ReviewEditor`.

## Plan

1. **SARIF through Porelo's profile reader (`org.fuin.porelo.intellij.sarif`, new, `@NullMarked`):** Take the hardened reader, the profile and its fixture documents from Porelo's published review API (`porelo-review-api`, its fixtures in its `tests` jar), named in `gradle/libs.versions.toml` and renewing `gradle/verification-metadata.xml` from an empty Gradle home when it is released. The plugin reaches it through one narrow interface, a document's bytes in and typed notes or a refusal by name out, so the reader replaces a stand-in without touching steps 2 to 4. Over it, a `ReviewDocument` that turns one validated document into typed `Note` records (anchor, side, thread, reply, state, origin, level, fix, outdated) and a `Submission` writer that builds a person's comment from the allowed fields only. Red first in unit tests over the published adversarial fixtures and a few of the plugin's own: an oversized document, nesting past the limit, a duplicate key, an unknown property, a scheme or `..` in `artifactLocation.uri`, a bidi or zero-width character in `message.text`, a fix outside its `new`-side anchor, and a daemon-owned field in a submission are each refused before binding.
2. **`Gate` (`org.fuin.porelo.intellij.gate`):** Add `comment`, `comments` (every page of one run, cursor followed, last page's completeness kept) and `resolveThread`. Read the new `PendingPush` fields into `PendingPush` and a `ReviewSummary` record, `base` into `Review`, `riskClass` into `Review.File`, each absent field kept absent. Map each refusal of section 1 in `Gate.refusal` to a `GateException` in words, as `MovedSinceReviewException` does today. Red first in `GateTest` against `VarlinkServer`: a comment sent and its stamped document read back, a retry with the same `id`, a paged `Comments` whose first page says `complete` and whose last says `partial`, a cursor answered for another run, and each named refusal said in words. Built: each of its twelve guards (the approvals edge, the id's grammar and length, the page bound and a repeated cursor, the thread's echo and both states, a moved push and every refusal storing nothing, and `toForge` never sent) seen red by a one-line change to `Gate` and green again.
3. **Anchors and threads against `ReviewCache` (`org.fuin.porelo.intellij.ide.ReviewTab`):** In `ReviewTab.read`, check `Review.base` against `changes.base()` and refuse a review whose base differs, then page each run of `ReviewSummary.runs` off the UI thread into `ReviewTab.Read`. Resolve each note's path, region and side as a pure function against the pinned blob bytes from `ReviewCache.files`, into current `line` threads per file and side, and `file`, `general`, outdated or unplaceable threads for the panel. Red first in `ReviewTabTest`: a thread on a path that is no regular blob at its side, or on lines beyond the blob, goes to the panel as unplaced rather than onto the diff, and an `old`-side or out-of-range fix gets no preview.
4. **`ReviewEditor`, `WaitingTree` and `Decisions` (`org.fuin.porelo.intellij.ide`), and the `Threads` adapter:**
   - In `WaitingTree.Renderer` and `ReviewEditor.header`, show the push's source level, risk class, `approvalsNeeded`, the open counts and each run's state.
   - Implement `org.fuin.porelo.intellij.review.Threads` over the daemon and set it on each diff request as `Threads.KEY` beside `ReviewContext.KEY`; `follow` tells its follower on the UI thread, and its stop may run more than once. `WatchProjects` is not sent again when a push's comments change, so a followed file's runs are read again after each of the person's own writes and while the tab is shown, and a read that fails says so instead of showing the old threads as current. `requestNew(context, side, range)` opens the editor for a new comment on those lines, sent through `Gate.comment` off the UI thread with a fresh `id`, and a refusal is said in words. Replies and resolving go the same way. Extend `CommentThread` with what a thread shows: its comments, each with origin, level and body, its state and its fix.
   - `ReviewContext` gains the old path of a renamed file, so an `old`-side thread on a rename resolves against the base's path.
   - Add the discussion panel in `ReviewEditor` for `file`, `general`, outdated and unplaced threads, and show `result.fixes[0]` inside its comment as a read-only `SimpleDiffRequest` over the cached blob bytes with no apply action.
   - Keep `Decisions.approve` bound to `entry.push().commit()` and independent of thread states, verdicts, suppressions and counts; `Decisions.reject` calls `gate.reject` as today.
5. **Against the stand-in, then the daemon (`LiveGateTest`):** First against a stand-in daemon that serves the comment calls, then on a VM against a real daemon that takes SARIF comments: write a line comment with a suggestion, a file comment and a general comment, read them back, resolve and reopen a thread, reject the push so the task receives the open threads, and see the task's reply arrive with its daemon-stamped origin and level.

## Acceptance

- On a VM against a real daemon: a line comment, a file comment and a general comment written in the review tab reach the task as SARIF 2.1.0; an anchor outside the pinned blob, a path with a scheme or `..`, a bidi or zero-width character, or a fix outside its `new`-side anchor is refused in words; the agent's reply appears in the thread with its daemon-stamped origin and source level. Each seen to fail first against today's plugin.
- A suggestion is shown as a read-only diff preview, and the working tree of any project open in the IDE is unchanged afterwards.
- Each run's state, the push's source level, risk class and `approvalsNeeded` are shown; a run that is not complete never reads clean; and resolving every thread, a verdict, a suppression or a count of zero never enables or performs approval on its own.

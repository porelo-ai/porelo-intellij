# IJ12 — The Code Review Adapter Over collaborationTools

**Status:** Idea; blocked by `porelo` [B291](https://github.com/porelo-ai/porelo/blob/main/issues/base/README.md#b291), [B292](https://github.com/porelo-ai/porelo/blob/main/issues/base/README.md#b292).

**What must be true.** The IntelliJ plugin attaches inline comment threads, gutter controls, and multi-line range commenting to Porelo's diff viewers through one narrow, replaceable pure-Java adapter package over the platform's `intellij.platform.collaborationTools` module, without exposing experimental JetBrains types to the rest of the plugin, depending on `qodana-sarif` or internal JetBrains classes, or altering non-Porelo diffs.

## To be checked

- **Spike on IntelliJ IDEA 2026.1+ and Plugin Verifier:** Wire `bundledModule("intellij.platform.collaborationTools")` in `build.gradle.kts` (and `src/main/resources/META-INF/plugin.xml` if required) and verify with `./gradlew verifyPlugin` across the IDE versions in `gradle.properties` (2026.1 and newer) that isolating all `@ApiStatus.Experimental` `com.intellij.collaboration.ui.codereview.*` calls (`DiffViewerUtilKt.showCodeReview`, `CodeReviewEditorModel`, `CodeReviewInlayModel.Ranged`, `CodeReviewCommentableEditorModel.WithMultilineComments`, `CodeReviewEditorGutterControlsModel`, `CodeReviewComponentInlayRenderer`, `CodeReviewCommentTextFieldFactory`, `CodeReviewFoldableThreadViewModel`, `CodeReviewResolvableItemViewModel`) behind one adapter package compiles and passes verification without touching `@ApiStatus.Internal` classes (`CodeReviewNavigableEditorViewModel`, `CodeReviewSubmitPopupHandler`, `TimelineDiffComponentFactory`), bundled GitHub or GitLab plugin classes (`GHPRReviewCommentBodyComponentFactory`), or `qodana-sarif`.
- **Pure-Java bridge to Kotlin `StateFlow` and coroutines:** Confirm how pure Java 25 code in the adapter package constructs and updates the Kotlin `StateFlow` / `MutableStateFlow` instances and `CoroutineScope` lifecycle that `DiffViewerUtilKt.showCodeReview` and the `collaborationTools` view-models take, with no Kotlin sources in the repository.
- **Attaching only to Porelo's diff viewers via a context tag in `ReviewEditor`:** Confirm that setting a Porelo `Key` with the authenticated review context (`projectId`, `repositoryId`, base and head commit SHAs matching `porelo/baseRevisionId` and `versionControlProvenance[0].revisionId`, and the file path) on each `SimpleDiffRequest` created in `ReviewEditor.showSelected` (`DiffRequest.putUserData`) lets the `DiffExtension` attach exclusively to `ReviewEditor`'s `DiffRequestPanel` viewers and ignore every other diff in the IDE.
- **Coordinate mapping between SARIF and IDE diff viewers:** Verify the conversion between SARIF 2.1.0 1-based inclusive `startLine`/`endLine` (`columnKind: "unicodeCodePoints"`) and `porelo/diffSide` (`old` or `new`) and the 0-based `LineRange` and diff `Side` (`Side.LEFT` and `Side.RIGHT`) in both side-by-side and unified diff viewers.
- **Disposal lifecycle:** Verify that switching files in `ReviewEditor`'s `SimpleAsyncChangesBrowser` (where `ReviewEditor.showSelected` calls `diff.setRequest` with a new `SimpleDiffRequest`), clicking *Read Again*, or closing the review tab (`ReviewEditor.dispose`) cleanly disposes every inlay, gutter control, listener, and coroutine scope without leaking editors or models.
- **SARIF dependency isolation and verification metadata:** Confirm whether [B292](https://github.com/porelo-ai/porelo/blob/main/issues/base/README.md#b292)'s hardened `com.contrastsecurity:java-sarif` 2.0 and maintained Jackson 2.x set is consumed through `porelo-wire` or bundled directly in `gradle/libs.versions.toml` and `build.gradle.kts` with classloader isolation so it never clashes with IntelliJ's platform libraries, and renew `gradle/verification-metadata.xml` from an empty Gradle home as [IJ09](README.md#ij09) requires before [IJ04](README.md#ij04) builds on the adapter.
